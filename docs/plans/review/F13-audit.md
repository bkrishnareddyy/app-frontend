# F13 Chat Interface — Audit

Overall readiness: **~32%**

Tool coverage: **17 of 19** spec'd tools implemented as callable model tools (11/11 read tools, 6/8 write tools). Missing: `upload_document` (no model-callable tool — handled entirely client-side, bypassing the tool-calling loop), `create_scenario` (no tool, no chat path to create a `LandedCostScenario` at all). Registry also ships 7 tools beyond the spec (`get_value_at_risk`, `get_team_members`, `create_shipment`, `search_products`, `search_parties`, `search_documents`, `export_compliance_record`) — good extra coverage, but not what was asked for.

**Headline claim check — "All UI actions must be doable via chat" is FALSE today.** The backend tool registry can technically invoke most write actions (approve/reject/resolve/classify), but the founder's own bar is broken in at least three independent ways: (1) the model powering `/api/assistant/chat` is still Gemini, not Claude, contradicting Task A-5 outright; (2) the chat UI renders **no** decision/exception/duty-stack/document cards and has **zero** inline approve/reject/resolve buttons anywhere in `ChatClient.tsx` — a user can only trigger a write tool by getting the model to call it from free text, there is no clickable UI for it; (3) chat-originated writes are indistinguishable from UI-originated ones in `AuditLog` because the table has no `source` column at all. Two of the four "Chat as Compliance Interface" capabilities (D-2, D-3, D-4) are entirely unimplemented — the compliance-advisor half of the feature barely exists.

## Cross-cutting Quality Standards violations found

1. **No fake data, ever (#1)** — `templateFallback()` in `advisory/query/route.ts:27-40` returns canned legal boilerplate indistinguishable from a real answer whenever the Gemini call fails or the API key is missing, rather than an honest error/empty state.
2. **Tenant isolation (#3)** — generally respected in the delegated route handlers the tools call through, but `run_impact_analysis` and `generate_reasonable_care_record` chat tools have no `access` gate at all (contrast with `generate_reasonable_care_record`'s UI-equivalent route requiring `documents.read` — see B-3), which is inconsistent even though not a cross-tenant leak per se.
3. **Vitest per capability (#4)** — the entire shipped assistant/advisory code path (`src/modules/assistant/*`, `src/app/api/assistant/*`, `src/app/api/advisory/query`) has **zero** direct tests. The 7 `copilot-*.test.ts` files test a different, unused module (`src/modules/copilot/copilotService.ts`, whose `askCopilot` export is called from nowhere in `src/app`) — this is effectively dead code with excellent test coverage sitting next to live code with none.
4. **Every write goes to AuditLog (#5)** — technically satisfied (writes are audited via delegated route handlers), but the schema cannot express *which surface* originated the write (see C-3), which is a direct, named requirement of this specific feature (`source: "CHAT"`), not just a generic nice-to-have.
5. **No `any` types / type safety (#7)** — tool `execute()` handlers routinely do `rawArgs as ListShipmentsArgs` (`tools.ts:178`) and similar unchecked casts instead of real runtime validation, meaning malformed/malicious model-generated tool arguments are trusted rather than validated — weaker than the "Zod schema, validated server-side" design B-1 calls for.
6. **Pagination on all list endpoints (#8)** — `GET /api/assistant/chats` has no cursor/limit params (hardcoded top-10), violating both this global standard and Task A-2 explicitly.

## Top 5 fixes ranked by severity

1. **Wire Claude into the chat and advisory surfaces.** `@anthropic-ai/sdk` is installed and proven working in `src/app/api/products/[id]/enrich/route.ts`, but `orchestrator.ts` and `advisory/query/route.ts` both still hard-code `GoogleGenAI`. This is the plan's most explicit, most testable requirement (Task A-5, D-1) and it was simply not done — the dependency was added but never used where it matters.
2. **Build the missing decision/exception/duty-stack/document cards and wire real inline actions.** `ToolCard()` returns `null` for 16 of 24 tools including every consequential write tool. Until this exists, "approve/reject via chat" is a theoretical capability the model *could* invoke from free text, not something a user can actually click — which directly breaks the founder's stated hard requirement that chat be a full second surface for the UI.
3. **Add a `source` (or `channel`) column to `AuditLog` and set it to `"CHAT"` from the assistant tool handlers.** Right now there is no way — none — to answer "was this approval done via chat or the browser?" from the audit trail, which matters a lot for a compliance product whose whole pitch is provable audit trails.
4. **Implement D-2/D-3/D-4** (why-this-HTS-code, duty exposure risk ranking, filing readiness explanation). The underlying data/services already exist (`classification-rationale` route, `filingValidator`, `get_duty_stack`) — these just need to be wired into chat/advisory tools and are the highest-value, lowest-effort wins available.
5. **Fix the `reject_decision` permission-label mismatch** (declares `decisions.approve`, route actually needs `decisions.reject`) and add real `access` gates to `run_impact_analysis`/`generate_reasonable_care_record` to match their UI-route equivalents. Not exploitable today (defense-in-depth in the delegated routes saves it), but it's a landmine for the next person who adds a tool assuming the `access` field is authoritative.
