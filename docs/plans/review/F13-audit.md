# F13 Chat Interface — Audit
> Re-audited: 2026-08-13 (second pass, compares against prior audit of same date)
> **Scoring note**: The user has confirmed Qubere is intentionally sticking with Gemini as the chat/advisory model — Claude is NOT a requirement. Task A-5 and the model-choice portion of D-1 are scored as satisfied by design; they are no longer counted as gaps. The Anthropic SDK integration exists in the code as a working, tested alternate path but is not required to be active.

Overall readiness: **~52%** (previously 32%; the 48% figure from this same re-audit pass has been revised upward now that the Claude requirement is removed)

Tool coverage: **17 of 19** spec'd tools implemented (unchanged from previous audit — `upload_document` and `create_scenario` are still not model-callable tools). The registry grew from 24 to **27** total tools (3 bonus tools added: `get_classification_rationale`, `get_duty_exposure_risks`, `validate_shipment_filing`, covering D-2/D-3/D-4), but neither of the two spec-required missing write tools was added.

**Headline claim check — "All UI actions must be doable via chat" is still FALSE today**, though real ground was covered. Genuine fixes: Zod runtime validation replaced trusted type-casts on tool args; `templateFallback()` (the silent-canned-boilerplate bug) is gone; 23 of 27 tools now render structured cards, including real inline Approve/Reject/Resolve buttons; D-2 and D-4 (HTS rationale, filing readiness) went from entirely unimplemented to fully wired; the `reject_decision`/`generate_reasonable_care_record`/`run_impact_analysis` permission-gate bugs are fixed; real Vitest coverage now exists for the shipped path and passes. Remaining, adversarially-verified problems that are NOT related to model choice: (1) the new `AuditLog.source` column is **never actually set to `"CHAT"`** by any route the chat write-buttons call — `decisions/route.ts:427` and `exceptions/[id]/route.ts:64` both hardcode `source: "UI"` regardless of the `x-qubere-source: CHAT` header and `source: "CHAT"` body field the client faithfully sends (94 hardcoded `"UI"` call sites repo-wide, zero that read the header/body signal) — so provenance tracking looks fixed but is functionally identical to before; (2) the new inline "Resolve Exception" button in chat (`ChatClient.tsx:1489-1499`) omits the server-required `expectedVersion` field, so every click 400s server-side, yet the code unconditionally shows `alert("Exception resolved.")` — this button is **guaranteed broken** on every use, and the Approve/Reject buttons have the identical no-`res.ok`-check pattern, so any real failure (permission, stale version) is silently reported to the user as success; (3) the new "duty exposure risk" tool computes `NaN` for essentially every classified line item due to a duty-rate parsing bug.

## Cross-cutting Quality Standards violations found

1. **No fake data, ever (#1)** — FIXED for the previously-flagged `templateFallback()` case (removed). **New violation found**: `get_duty_exposure_risks` (`tools.ts:1107`) silently produces `NaN`/garbage dollar figures for real data due to a rate-parsing bug — presented in a polished card (`ChatClient.tsx:1610-1629`) as if it were a real number, which is arguably worse than an honest empty state.
2. **Money is always Decimal.js (#2)** — new violation: `get_duty_exposure_risks` (`tools.ts:1104-1120`) does duty math with plain JS `number`, not `Decimal`, unlike the codebase's established `dutyEngine.ts` pattern it sits next to.
3. **Tenant isolation (#3)** — still generally respected via delegated routes; `run_impact_analysis` and `generate_reasonable_care_record` now have explicit `access` gates (fixed, see B-3), closing the inconsistency flagged last time.
4. **Vitest per capability (#4)** — FIXED for the shipped path: `tests/assistant-orchestrator.test.ts`, `tests/assistant-tools.test.ts`, `tests/assistant-advisory.test.ts` now exist and pass (9 tests, verified via `npx vitest run`). Coverage is thin (no mocked-Anthropic-response assertion, no B-5 tenant-isolation test) but real. The unused `copilot-*.test.ts` files (testing dead code) are unchanged/still present alongside.
5. **Every write goes to `AuditLog` (#5)** — writes are still audited, but the specific, named requirement of this feature (`source: "CHAT"` distinguishing chat-originated writes) is **still not functionally true** despite the schema now supporting it — see C-3 above. This is the most consequential "looks fixed, isn't" finding in this pass.
6. **No `any` types (#7)** — substantially improved: the previous `rawArgs as X` casts in `tools.ts` are gone, replaced by real Zod `safeParse`.
7. **Pagination on all list endpoints (#8)** — FIXED for `GET /api/assistant/chats` (cursor-based, capped at 50).
8. **New: unchecked response status before user-facing success confirmation** — not an enumerated Quality Standard but a serious data-integrity smell: `ChatClient.tsx:1437-1499`'s three new inline action buttons all call `fetch()` and immediately `alert("...successfully")` without checking `res.ok`, so failures are misreported as successes to the user — directly undermining the product's "provable audit trail" positioning.

## Top 5 fixes ranked by severity

1. **Wire the `source` signal the client already sends into the routes that matter.** `decisions/route.ts:427` and `exceptions/[id]/route.ts:64` (and `productService.ts`'s ~5 call sites) hardcode `source: "UI"` even though the chat UI and every chat write-tool already send `x-qubere-source: CHAT` / `source: "CHAT"`. This is a small, mechanical fix (read `body.source` or the header, pass it through to `createAuditLog`) that closes the single most-cited gap from the prior audit — right now it only looks closed.
2. **Fix the `Resolve Exception` chat button, and add `res.ok` checks to all three inline action buttons.** `ChatClient.tsx:1489-1499` omits the server-required `expectedVersion`, guaranteeing a 400 on every use while telling the user it succeeded. Approve/Reject have the same silent-failure pattern. This is currently a demo-breaking bug in newly-shipped, user-facing code.
3. **Fix the duty-rate parsing bug in `get_duty_exposure_risks`.** Swap `Number(hts.generalDutyRate ?? 0.05)` for the existing `parsePublishedDutyRate(hts?.generalDutyRate)` helper already imported into `tools.ts` via `dutyEngine.ts`, and use Decimal.js for the arithmetic. Without this, D-3's headline "duty exposure risk ranking" feature returns `NaN` for real accounts.
4. **Build A-3 session context (`shipmentId`/`clientId`/`documentId`) and the C-1 context panel.** This remains the largest structurally-missing capability — without it, chat cannot be scoped to "this shipment's workspace," which is central to the plan's "second surface for the UI" framing.
5. **Fix the A-1 multi-turn-memory bug only if the dormant Anthropic branch is ever activated** (low priority since Gemini is the confirmed permanent choice) — otherwise consider removing the unused Anthropic branch to reduce maintenance surface, since it is not required and currently carries its own untested bug.
